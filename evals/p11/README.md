# P11.5 本机负载实验

本文保留历史实验方法。文中的冻结镜像和旧运行时归档不随仓库发布，不能把当前代码套用旧迁移当成历史版本。当前发布检查从根目录运行`scripts/check_release.py`，公开结果与限制见[验证说明](../../docs/validation.md)。

`load-contract.json`在首次测量前冻结。数据、资源、到达率、持续时间、重复次数、分位数算法与验收目标写在同一材料中；失败和探索档不移除，修改协议须另起版本。默认不调用真实模型、读取邮箱或使用开发库。

使用`scripts/benchmark_p11.py --suite reads|isolation|pipeline --phase before|after --output 新目录`运行。依赖已构建本地镜像`job-agent-p11-local:20261028`、`pgvector/pgvector:pg16`和Docker；使用实际PostgreSQL16，不启用pgvector扩展。脚本挂载当前benchmark模块作为明确的模型替身，只向临时容器传递新生成的配置，绝不装载用户真实.env。需要项目Python环境及容器权限。

每个试验创建独立Compose项目和数据库卷，实测CPU/内存限制，保存逐请求结果、P50/P95/P99、队列、容器CPU/内存、数据库连接/锁等待与清理记录。负载生成器在Mac上运行，不在服务资源上限中；Docker虚拟机和同机开销必须随结果说明。

before使用0001～0011迁移；after追加0012索引，其余镜像与业务代码相同。共享连接/独立worker对照使用同一当前源码的兼容同步路径与默认队列路径，重现P11.0问题；不冒充运行历史源码。为建立5个重叠模型等待，只有该对照临时提高有效槽位至5；正常混合与故障实验使用2个槽位。

逐请求区分预约发送时间至响应、实际发送至响应和客户端调度滞后。请求超时/HTTP错误不从分位数中删除；超过客户端并发上限的到达记录为client_dropped，独立计入交付率，不伪造0ms延迟。预热材料单独保存，不合并到测量。每个档位分别重复，不先混合样本再选有利数字。

模型固定等待与可注入429/超时都是替身，不代表真实模型吞吐或准确率。队列提交202和任务最终成功另行核对；业务/回执/任务数必须能对账。原始结果在项目`.work/p11/p11.5/`，历史报告保留，公开描述以最终阶段文档为准。


## 两阶段优化及冻结镜像

索引对照18轮、共享池/队列6轮及主管道4场景使用同一冻结镜像。发现231.786ms未达标后，另立补充三轮对照：`benchmark_p11_burst_compare.py --output 新目录`仅切换准入优化前后镜像。旧版服务源码快照`baseline/jobs_before_merge.py`及`baseline/Dockerfile`可帮助跨机重建。

仅在没有原冻结镜像的新环境中，先构建当前代码为`job-agent-p115-local:20261029`，再用`docker build -f evals/p11/baseline/Dockerfile -t job-agent-p11-local:20261028 .`重建准入基线；这不是原二进制，必须记录新镜像ID并另跑，不合并历史数据。已有冻结镜像不要覆盖。PostgreSQL镜像身份和实际版本在host-environment.json中；标签可能漂移，跨机复测应核对镜像ID与PG16.15。

合并后服务端P95三轮59/59/79ms，但客户端83/410/86ms，不宣布突发端到端200ms全部通过。原始未达标轮次、客户端/服务端测量边界与后续定位需求见项目P11.5报告。`burst_compare_as_run.py`保留首次补充试验的实际脚本，后续只增加输出目录参数。


## P11.6之后的版本边界

上面的“当前代码重建P11.5”步骤只适用于P11.5源码快照。截至0013，API/worker已依赖新增观察表/列，仅替换jobs_before_merge.py不能从当前P11.6还原P11.5完整运行时。已有两个P11.5冻结镜像继续保留；跨机应先取得完整P11.5源码版本/归档再重建并记录新镜像身份，不能把当前版本套旧迁移称作历史基线。

新增`diagnose_p116_latency.py`只跑after迁移与P11.6独立镜像；原benchmark_p11.py和load-contract.json哈希未改。新建/预热连接各三轮逐请求配对，保留330ms慢轮和初始化失败补跑，不替换原410ms。条件、边界与复现见公开验证说明的性能实验章节。
